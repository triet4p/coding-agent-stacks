# Implement Atomic Task Skill

## Purpose
This skill is the shared procedure for one atomic task across the `bronze-task`, `silver-task`, and `gold-task` roles. It covers implementation, route-appropriate verification, optional evidence records, qualified advisor requests, and handoff. Workers follow the assigned role and route, never reroute themselves, and report role only without model metadata per `~/.agents/rules/subagent-routing.md`. Main owns routing, planning, status, and gates per `skill://omp-subagent-flows`.

## Workflow
### 1. Implement One Concern
- Read the assigned acceptance criteria and project conventions; change only what is needed for that concern. Respect the assigned role and route (light default vs full); never copy a selector from a skill, template, or prior attempt.
- Keep the task **[~] in progress** while implementing and correcting findings; do not mark your own work [x]. Follow the assigned route, report evidence and remaining criteria plainly, and never reclassify your own task. A finding alone forces neither a role change nor an advisor request.
- Do not end an unfinished attempt merely because a request, elapsed-time, or token count was reached. With the soft request budget disabled, continue safe in-scope work while making progress; Main decides continuation/replacement. Pause unsafe work or work blocked by missing prerequisites and report why. Unavoidable runtime/provider/context limits do not constitute completion.
- On a matching `progress_request`, reply compactly with the task/attempt/agent IDs, request/timer IDs, `stage`, `completed_since_last_report`, `new_evidence`, `current_blocker`, `attempts`, `results`, `next_action`, `help_needed`, and `advisor_needed: false|true`. Report new evidence and the next safe action, not merely elapsed effort; the qualified advisor-request rules below still apply.
- When Main/user pauses the attempt or requests replacement, write a detailed handoff as a separate attempt-scoped file under the assigned project's `artifacts/` directory (or the explicit assigned output root for non-project work), never as a section in the task summary or sprint plan. Before ending, acknowledge its exact saved path with matching task/attempt/agent IDs. Preserve the goal and acceptance criteria; satisfied and remaining criteria; current state, changed paths, ownership, and unrelated user changes; decisions and rationale; exact verification commands/scenarios and observed results; tried or rejected hypotheses; blockers and unresolved findings; next safe actions and required checks; relevant prior attempts and agents with their artifacts/reports/checkpoints and actual history URIs/ranges; and access gaps. Keep prior attempt handoffs intact. Resume a paused attempt only when authorized. If runtime forces an end before saving, disclose the missing handoff; never fabricate one. A bare yield or submit is not completion. Claim `implementation_complete` only when assigned criteria and required material verification are satisfied; assigned review/checkpoint gates still apply.
- As a continuation or replacement worker, you are explicitly authorized and required to read the supplied prior-attempt handoff file and relevant histories directly before substantive work. Use supplied task/attempt/runtime-agent IDs to correlate evidence; avoid repeating rejected approaches without new evidence. Report missing or inaccessible references to Main before proceeding; a summary does not replace required history access or prove the current snapshot.

### 2. Verify Behavior
- Exercise the changed behavior with the most specific runnable command or scenario; record what ran and what was observed. Run affected existing tests when the changed contract requires it.
- Add or update a **permanent automated test only when it protects an observable behavior against a plausible regression**. Do not create a test just to satisfy a checklist, assert incidental wiring or source text, or substitute a test file for a runtime smoke check.
- For a documentation or workflow-only task, check the edited instructions and their cross-references instead of inventing an automated test. Report any verification limitation honestly.
- If a bounded, evidence-backed unresolved technical question or material uncertainty could benefit from diagnostic input—even before repeated failures—send one qualified Main-brokered `advisor_request`; competing plausible hypotheses with no safe discriminating next action are one example. Repeated failures, no new evidence across distinct attempts, and an unchanged blocker are examples, not prerequisites. Elapsed time or a fixed attempt count alone, a generic request, or open-ended task delegation does not qualify. Include matching `task_id`, `attempt_id`, unique `consultation_id`, goal/criterion, blocker, bounded relevant evidence, tried hypotheses/results (or say none were safely tested), constraints, and one exact actionable question. Never spawn an advisor. On every matching progress request, return `advisor_needed: false|true`; `false` is a cheap decline, while `true` without a complete request is pending interest only and never launches help. Include the complete request in that reply when qualified, or send one qualified request directly; advice is not evidence, so independently try relevant advice and record its observed result.

### 3. Record Task Evidence

- A task summary is optional for ordinary light-route work. It is REQUIRED when an assigned review/checkpoint gate needs worker evidence, Main assigns a summary, or meaningful evidence must be preserved for an assigned review or handoff. Write it under the assigned project's `artifacts/` directory (or the explicit assigned output root for non-project work), using the [task-summary template](./references/_ARTIFACT_SUMMARY_TEMPLATE.md). Resolve the path from the assignment; never infer it from cwd, use `local://`, or write under an unrelated global root.
- Keep the task summary lightweight: record the observable result, changed files, assigned subagent role, route and selection basis, relevant dispatch/history refs, quota/cost observation or `unknown`, relevant scope, actual verification, commit status and concrete open findings. Never include model/provider names, selectors or effort values. Omit unassigned review/checkpoint sections; add no telemetry or unperformed checks. Detailed pause/replacement handoff and Main's temporary supervision state belong in separate attempt-scoped files, not the summary or a plan.
- Keep implementation details in this artifact. The worker's final handoff to Main is compact: task/attempt IDs, outcome, changed paths, exact verification result, artifact path, and unresolved findings or advisor reference. Do not send full histories, trajectories, or logs.
- An evidence reviewer examines a task only when Main assigns an evidence gate. A required full-route review and an explicitly assigned optional light-route review are both binding: actionable defects or material unverified criteria mean FAIL, and a failed gate is not ignored. The reviewer writes its own report under the assigned project's `artifacts/` directory (or explicit non-project output root); it does not edit the worker summary. Main receives a compact verdict, findings, and the report path.
- Project work has no automatic commit, review gate, or checkpoint. On the light route, a worker MAY commit only its own verified scope when the assignment explicitly authorizes the commit and identifies the exact repository, Git directory, worktree, target ref, and staging ownership; no foreign staged changes may be included, and amend/rebase/history rewrite or hook/signing bypass is forbidden. Push requires separate explicit authorization. Full-route workers do not commit. Only a fresh explicit `bronze-task` agent may execute an explicitly authorized full-route checkpoint-only assignment after matching evidence PASS, against its exact frozen snapshot; it edits no source and owns a separate checkpoint record. `silver-task` and `gold-task` never execute full-route checkpoints. A worker summary, reviewer report, or authorized light-route worker commit is not a substitute for a required full-route checkpoint record.

### 4. Complete Assigned Gates

- Apply only the gates assigned to the route. Light-route work has no automatic evidence review or project checkpoint; it may be accepted after its assigned criteria are met, including an explicitly authorized worker-owned commit when assigned. If an optional light-route evidence review is assigned, it is binding and a FAIL blocks acceptance. Full-route work has the explicitly required evidence gates and, at its pre-agreed project boundary, a fresh Bronze-only exact-snapshot checkpoint after a matching PASS; Main authorizes the executor and decides whether its separate record establishes success. Main—not the worker or reviewer—owns review/checkpoint assignments and [x] status. Failed required gates block completion; do not silently downgrade them.
- Any Git operation needs an explicitly assigned and authorized repository, Git directory, worktree, target ref, and ownership scope. Missing repository information does not turn project work into non-project work and never authorizes a fallback repository or automatic Git action. Project-backed light work may finish verified and uncommitted when no commit was assigned. If a commit was assigned but fails or is unavailable, report `commit_pending`; do not mark that assignment complete. Explicit non-project work uses its assigned output root without inventing a project Git requirement.
- If content changes after a PASS for an assigned review/checkpoint, obtain a fresh review before another checkpoint. Any later correction uses a separate new commit when authorized; never amend an earlier checkpoint or bypass applicable hooks/signing.
- Each role owns only its assigned records: the implementation worker may write its own task summary and separate handoff; the reviewer owns its report and, only when required for a planned full-route checkpoint, the frozen-snapshot manifest; the fresh Bronze checkpoint executor owns its checkpoint record. Main owns planning, routing within user authority, status, and any separate supervision files. Keep all such records under the assigned project `artifacts/` directory or explicit non-project output root. Advisor requests remain available to implementation workers under the rules above; reviewers and checkpoint-only executors do not request advisors.
