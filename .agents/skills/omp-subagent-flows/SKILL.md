# OMP Subagent Flows

## Scope

Use this skill only inside **Oh My Pi (OMP)** when a user requests feature implementation that belongs in a plan or sprint.

Never use this workflow in Codex CLI, Claude Code, or any other coding-agent CLI. Never translate its OMP agent names, tools, lifecycle operations, or artifact URLs to another runtime.

The main session is only an orchestrator and plan manager. It may inspect and edit plans, select and brief agents, match compact task/attempt-correlated summaries to current attempts, coordinate workflow transitions, and decide gates. On the light route it may also inspect enough of a worker's completed result and its assigned verification evidence to make its own acceptance check; it never reads full agent histories, edits product/source files, debugs, executes sprint work or Git operations, or writes worker, evidence, review, log, or checkpoint records. Its durable edits are plans — keep statuses current and add concise outcome/gate/checkpoint summaries with links to the worker artifact, reviewer report, frozen PASS reference, and executor checkpoint record — plus Main's own separate supervision, handoff, and temporary-state files, written under the assigned project's repository `artifacts/` directory (or the explicitly assigned output root for non-project work) as described below. Never copy artifact details into a plan.

## Route selection: light default, full by condition

Main selects the route for each task or atomic batch before dispatch, repeats it with exact required gates in the worker brief, and records it in an existing sprint plan's workflow line when a plan is needed. A bounded light fix needs no new plan.

- **Light is the default for bounded, low-risk work** with a clear acceptance contract: the worker implements the assigned concern and runs the specific behavior check named in its brief. An evidence review is optional on this route and is assigned only when risk, evidence preservation, or the user requires it; once assigned, it is binding and a FAIL is not ignored. A worker may commit its own verified scope only when the assignment explicitly authorizes that commit. Light-route work has no automatic per-task evidence gate, no automatic project checkpoint, and no deep review merely because the work was called a sprint. Project-backed light work may finish verified and uncommitted when no commit was assigned; an assigned commit that fails or is unavailable leaves the task `commit_pending`.
- **Full is for material risk, contract or interaction changes, or a user requirement**: explicitly required evidence gates per task, a separate Bronze-only exact-snapshot checkpoint at the pre-agreed task or batch boundary, and a deep review only when Main assigns one for meaningful cross-task risk. Required full-route gates cannot be dropped, merged, or downgraded at cutover; changing a route is a deliberate recorded decision, not a convenience.
- Gates declared on either route are mandatory. Main records the route, the exact assigned gates, and any commit authorization (or its absence) in the brief and any existing plan so a successor can see what was actually required.

## Routing ask and scoped authority

- Before dispatching any worker, Main asks the user to choose the role **unless** the user has already explicitly selected a role for the current work or granted scoped routing authority for a task, batch, session, or sprint. A prior selection or granted scope stays in force within its declared boundaries; Main does not re-ask for confirmation inside that scope.
- The ask presents these items together as one bounded question set: the bounded task and the reason for the recommended route; the configured effective model/effort from the role definition versus the model/effort actually observed at runtime for this run; the runtime quota observation, or `unknown` when it was not observed; the recommended route (light or full) and why; and whether commit authority is granted, with the exact repository, Git directory, worktree, target ref, and staging ownership when it is.
- Batch distinct questions into the same ask instead of serial one-question turns. Valid choices are the explicit `bronze-task`, `silver-task`, and `gold-task` roles plus Main self-selecting within its authority. The obsolete `task`/`hard-task` implementation roles are not valid choices, and OMP's bundled generic `task` tool/agent is never implicitly selected as a flow worker, reviewer, advisor, or executor.
- Never apply an implicit Gold default, and never resolve an uncertain Silver/Gold choice by automatic promotion. Without routing authority, ask; with routing authority, Main chooses from task fit and the user's constraints without re-asking. Bronze fits known procedures; Silver fits bounded reasoning with clear rules and a positive fit; Gold fits medium work involving context, design choices, diagnosis, or integration and needs no prior Silver failure. The user's stated quota/cost preference overrides tier stereotypes, and quota is reported as observed or `unknown` without fabricated measurements.
- Scoped routing authority persists for its declared scope only and never becomes persistent configuration: Main never writes routing decisions, selectors, or model choices into definitions, skills, plans as policy, or runtime settings. When the configured effective definition and the actual observed runtime model/effort differ, Main reports the mismatch honestly instead of substituting one for the other.

### Auto-routing for an unattended task sequence

- Accept explicit authority from an ordinary user/steer message, such as "Main tự chọn agent cho các task 3–8, không hỏi lại", or from an `ask` option labeled **"Auto cho dãy task này"**. Offer that option with the concrete covered task IDs/range or named batch/sprint and any role/quota restrictions in its description. Selecting one worker role alone does not authorize auto-routing for later tasks.
- Main acknowledges the covered scope and restrictions once, then autonomously selects and launches workers for that sequence, including in-scope correction and replacement attempts. Do not call `ask` again for role selection, routine escalation within allowed roles, unknown quota, or comparable Silver/Gold fit. Use known definitions, task evidence and the user's preferences; quota `unknown` is not a reason to wait for an absent user.
- Keep authority in the current task/sequence context and pass its bounded reference in worker briefs. It ends when the covered work completes or the user revokes/narrows it; unrelated/new tasks are not included. A steer changing authority governs subsequent dispatches and does not by itself cancel a live worker.
- Auto-routing is not extra commit/push, destructive-action, model-override or advisor-consent permission, and does not waive verification, required gates, detailed replacement handoff/history or async safety. Existing explicit permissions remain in force only within their own scope.
- If an action genuinely needs authority outside the grant or an unreachable prerequisite, do not invent consent or treat user silence as approval. Leave the affected task blocked with the concrete reason and continue only other safe, authorized work that is independent of it and does not cross a required boundary. Ask only for the genuinely missing decision; never block the authorized sequence on a redundant routing question.

## Invariants

1. Keep at most **two active subagents total**, including implementation workers, reviewers, advisors, and checkpoint executors.
2. Planning remains in the current main session and uses the **exact current model**. Never delegate plan creation or switch models for it.
3. Use a fresh worker for each task or correction; transfer the prior worker's artifact and unresolved findings instead of reviving an idle agent. **Explicit `gold-task` (Gold) is a general-purpose reasoning route for medium tasks, including context, design choices, diagnosis, and integration; `silver-task` (Silver) is directly eligible for well-bounded work with clear rules and a positive fit; `bronze-task` (Bronze) handles known procedures and is the sole checkpoint executor.** Reclassify each task independently; no medal is a sticky or implicit default. Main may auto-select within explicit user authority. Resolve model/effort from the effective definition. Main owns continuation and replacement; no fixed request/token count in this flow ends an attempt.
4. Run one sprint implementation task at a time. An `evidence-reviewer` runs only when its gate is assigned: always on the full route, and on the light route only when Main assigns one. Never batch task-level evidence reviews. A full-route project task also requires a separate Bronze-only exact-snapshot checkpoint at the pre-agreed task or batch boundary before the next independent project task; only a predeclared shared atomic batch, declared and approved as one checkpoint boundary before implementation, may continue through its included tasks before that single checkpoint.
5. Run a `deep-reviewer` only when Main assigns it for meaningful cross-task risk review, and only after every assigned per-task evidence gate and required full-route checkpoint has passed. A correction may require another assigned differential review.
6. A review with actionable findings does not pass. Correct the findings and run a fresh review at the same level.
7. The effective definitions for `bronze-task`, `silver-task`, `gold-task`, `evidence-reviewer`, `deep-reviewer`, and checkpoint-executor `bronze-task` assignments must be `blocking: false`; inspect project-level overrides before launch. If a flow definition is blocking, or async execution is disabled/unavailable, do not launch synchronously, silently repair an override, or edit runtime configuration; report the condition and wait for authorized resolution.
8. For work expected to exceed 5 minutes, every worker, reviewer, and checkpoint executor proactively messages Main with task/sprint ID, attempt ID, current stage, and reason it will run long. If that becomes clear only during execution, message then. Work lasting 5 minutes or less needs no proactive message. This notice is independent of timer supervision and is not a gate verdict.
9. Every subagent enumerates and reads all regular files under `~/.agents/rules/*` before substantive work, including corrections and replacements. Apply relevant rules at their proper precedence; report conflicts or inaccessible files instead of silently ignoring them.

## Roles

- **Main session:** plan management and summary-only orchestration. Main checks effective definitions before launch, never reads full worker histories, and never writes evidence, review, worker, or checkpoint records; on the light route it inspects enough of the worker's completed result and assigned verification evidence to decide acceptance itself. The bundled OMP generic `task` tool/agent exists outside this flow and must never be selected implicitly as a flow worker, reviewer, advisor, or executor; only the explicit `bronze-task`, `silver-task`, and `gold-task` implementation roles below are flow routes.
- **Worker:** a fresh Main-selected explicit `bronze-task`, `silver-task`, or `gold-task` subagent for one task or correction on the assigned route. Gold is eligible for medium reasoning and never an automatic default; Silver is equally eligible for bounded reasoning. Main selects within user routing authority; the effective definition supplies model/effort. Workers never reroute themselves. It owns implementation and any assigned task artifact; an ordinary light result may be compact without an artifact. For light work, a worker MAY commit only its own verified scope when explicitly authorized with the exact repository, Git directory, worktree, target ref and staging ownership; no foreign staged changes, amend/rebase/history rewrite or hook/signing bypass. Push needs separate authorization. Full-route workers do not commit; Silver and Gold never execute full-route checkpoint-only assignments.
- **Evidence reviewer:** a fresh `evidence-reviewer`, read-only on assigned source, worker artifact, and plan. It runs only when Main assigns its gate — required on the full route, optional but then binding on the light route — and once assigned, a FAIL is not ignored. It receives the worker artifact and may inspect the assigned source and worker history directly. It owns and writes its detailed report under the assigned project's `artifacts/sprint-<N>/reviews/` directory (or the explicit assigned output root for non-project work), and its frozen-snapshot manifest only when a full-route checkpoint is planned or the assignment explicitly requires one; Main receives only the compact verdict, reviewed-snapshot reference, findings summary, and report path.
- **Deep reviewer:** a fresh `deep-reviewer`, read-only on source and existing records, using its effective agent definition, that Main may assign for cross-task differential review after every assigned per-task gate and required full-route checkpoint has passed. It reads worker artifacts, evidence-review reports, and executor checkpoint records directly, treating cited passed gates and required checkpoint records as established ground; for light-route tasks without assigned gates it treats the worker's verified result and any explicitly authorized worker commit as evidence, and does not require records that were never assigned. It may inspect worker history directly when needed, but does not redo passed checks. It owns its report.
- **Checkpoint executor:** on the full route, after a matching evidence PASS, Main may assign a fresh, non-blocking async explicit `bronze-task` agent — only `bronze-task` may execute checkpoints; never `silver-task` or `gold-task` — a checkpoint-only assignment for the exact frozen snapshot. The executor does not edit product/source content or approve the evidence gate; it owns the checkpoint record under the assigned project's `artifacts/sprint-<N>/checkpoints/` directory (or the explicit assigned output root for non-project work). Main alone authorizes this assignment and decides whether its compact result establishes checkpoint success.

### Model resolution

Agent definitions are the single source of truth for model and effort. Resolve each named role from the installed user definition (`~/.omp/agent/agents/<role>.md`) and any effective project-level override before every launch. This applies to workers, advisors, both reviewers, and checkpoint executors; do not cache a selector from an earlier task or copy one from this or another skill.

Dispatch by explicit `agent` name and omit the task item's `model` override for normal flow execution, so OMP uses the effective definition. A deliberate override must be explicitly authorized and satisfy that definition's dispatch-consent policy; never invent unsupported fields or silently rewrite definitions/configuration. Changing a definition's model or effort requires no flow/skill edit. Reassess suitability using the currently resolved model's observed capabilities and relevant history rather than treating a medal label as a permanent model ranking.

Record the selector/effort actually resolved for each attempt as historical evidence, not a reusable dispatch constant. Requested effort is not proof of provider-applied effort; report the latter as unknown when not observed.

Resolve the record root from the active plan or assignment rather than from this global skill or the current working directory. Store task artifacts, reviewer reports, and checkpoint records below the assigned project's repository `artifacts/` directory; explicit non-project work uses its explicitly assigned output root. Never use `local://` for durable work records, never another project's artifacts, and never a global home log. Workers, reviewers, and checkpoint executors own their own records; Main writes only plan/status references, concise summaries, and its own separate supervision/handoff files.

### Handoff and temporary-state files

- Plans stay stable: scope, acceptance criteria, current status, milestones, durable decisions, real blockers, and concise outcome/evidence links only. Never put per-turn dispatch receipts, agent/model selection logs, progress requests, timer/wait events, tool retries, or copied handoffs and outputs in `docs/PLAN.md` or `sprint-<N>.md`. Routine coordination stays in chat and trace.
- Detailed handoffs and temporary supervision state are separate attempt-scoped files under the authorized repository's `artifacts/` directory: `artifacts/sprint-<N>/handoffs/` or `artifacts/sprint-<N>/state/` for sprint work, and `artifacts/<task-id>/` for a standalone task. Explicit non-project work uses its explicitly assigned output root. Never use a plan file, `local://`, another project's artifacts, or a global home root.
- A pause and a deliberate replacement require the same durable attempt-scoped handoff file, written before the attempt stops and acknowledged with its exact saved path. Required content: task/attempt/runtime-agent IDs and role, goal and acceptance criteria, current state, changed paths and ownership, decisions and rationale, verified results, tried and rejected hypotheses, blockers, remaining criteria, next safe actions, and references to all relevant earlier attempts/agents and their actual records and history URIs.
- Preserve prior handoff files and link to them instead of copying their contents into a plan. Do not create a file for every action: write one only on a pause, a replacement, or a genuinely needed durable supervision state. Main's own supervision state follows the same root rules and stays separate from plans and worker records.
- A paused attempt may resume on the same attempt ID when the user explicitly authorizes resumption; resume requires no replacement handoff and no new async job.

## Async jobs, events, interruption, and progress

### Launch and result acceptance

- Launch each flow agent as an asynchronous job and record the task ID, unique attempt ID, agent ID, returned job ID, and role. Give replacements a new attempt ID. The async launch/result and agent-message events are Main's supervision channels; progress messages are not completion events.
- Accept a worker, reviewer, or checkpoint-executor result only when it matches the current task ID, attempt ID, and agent ID, and that agent has completed. A launch receipt, message-delivery receipt, progress reply, partial handoff, or timer event is not task completion or a gate verdict.
- If an attempt is cancelled or replaced, invalidate it before continuing. Ignore any later result, message, or timer from that stale attempt for gate decisions; it must never advance the task or sprint.
- Check that the effective role definition has `blocking: false` and that async execution is enabled before launch. If OMP instead runs inline, reports no async job manager, or falls back to synchronous execution, stop and surface the configuration/runtime condition. Do not silently switch to blocking operation or edit runtime configuration.

### Main's event handling

- Main reacts to delivered job-completion and agent-message events. Do not repeatedly poll status. Use `functions.wait` only when Main is otherwise blocked with no useful work, and only to wait for an event; do not invent a timeout argument or use it as a timer.
- Never supervise workers with eval `handle.wait` or an eval barrier: aborting those waits can cancel the jobs being waited on. Do not attach worker lifetime to a Main-turn wait.
- A Main/user interrupt (including Escape where applicable) interrupts Main's current turn; it is not an explicit cancellation of a detached worker. To stop a specific worker, use the explicit cancellation control for that worker's async job (for an exposed process job, `proc://<job-id>/kill`). Do not confuse cancelling a job with interrupting Main.
- Do not promise detached-job durability across process exit or automatic Main resumption after a user interrupt. A subsequent user prompt may be needed for Main to process queued results.
- A send receipt confirms delivery only; it does not establish that the recipient read, applied, or acknowledged the message. A late reply or tool execution is not by itself evidence that the worker is stalled.

### One-shot timer supervision

- For every active attempt, Main starts exactly one finite background shell timer with an adaptive observation interval of **10–30 minutes**. Use an existing finite async shell timer (for example, a PowerShell `Start-Sleep` command launched through Bash with async enabled) that emits a marker containing the task ID, attempt ID, and timer-generation ID. This timer is an observation prompt, not a worker deadline or a reason to stop work.
- Choose the interval from current task context and observed progress, not from elapsed time alone. Keep only one timer generation active per attempt. Do not rearm/restart timers in a hot loop.
- On worker, reviewer, or checkpoint-executor completion, completion takes precedence: cancel its timer job if still active and invalidate that timer generation. If a completion and timer event race, handle completion first. Ignore a late timer whose task, attempt, or generation is no longer current.
- On a current timer event, Main sends exactly one outstanding `progress_request` to the matching agent, carrying `task_id`, `attempt_id`, `agent_id`, `progress_request_id`, and `timer_generation`. Do not issue another request while one is outstanding. For any implementation `bronze-task`, `silver-task`, or `gold-task` worker only (including corrections), when no advisor request, positive interest, or consultation is pending, Main includes the single field `advisor_offer: "Bạn cần advisor gì không?"` in that same request; it is not a separate message. Omit the offer while any advisor request, positive interest, or consultation is pending. Reviewers and checkpoint executors — including a `bronze-task` executor — never receive this offer.
- The matching progress reply carries all of those IDs and these fields: `stage`, `completed_since_last_report`, `new_evidence`, `current_blocker`, `attempts`, `results`, `next_action`, and `help_needed`. A worker additionally returns `advisor_needed: false|true` and may include one complete `advisor_request` payload when qualified; `false` is a cheap decline and triggers no follow-up, while `true` without the complete request is pending interest, not a consultation. A `true` reply or offer alone never launches an advisor. Reviewers and checkpoint executors do not consume implementation-advisor consultations. Main compares reported deltas and evidence; elapsed time alone is not difficulty or a stall. A timer event or progress reply never substitutes for completion or review.
- After a matching reply, if the same attempt remains active and no request is outstanding, Main starts the next one-shot timer generation at an adaptive 10–30-minute interval. Do not keep restarting the timer while a reply is pending. Workers continue to send the required >5-minute proactive notice independently of this timer.
- Do not automatically request help, replace a worker, or advance a gate solely because a timer expires. Keep implementation details in worker artifacts; Main's messages and plan remain orchestration-only.

### Main-owned continuation and replacement

- With the user-disabled soft request budget, Main supervises attempts through existing completion/message events and the one-shot progress timer; do not reinstate a fixed request, elapsed-time, or token cutoff in prompts, or change runtime settings. Runtime/provider/context limits still apply; a forced stop is not success.
- Continue an active attempt while it adds discriminating evidence or completes remaining criteria. Workers do not voluntarily submit unfinished work merely because a request/token count was reached. Pause unsafe or blocked work, report the concrete reason, and let Main decide continuation or replacement.
- After roughly **4–5 matched progress exchanges** on an attempt, Main explicitly reassesses progress, blocker, and next safe action: continue with a reason, narrow the remaining brief without dropping acceptance criteria, or replace. This is an evaluation checkpoint, not a hard deadline or automatic role switch; repeated hypotheses without new evidence warrant earlier intervention. A sent request or delivery receipt is not a completed exchange.
- An unanswered request is not evidence of success or, by itself, a stall. If silence persists, use an adaptive one-shot observation timer to prompt a Main reassessment without sending duplicate progress requests or polling in a loop; consider delivered runtime errors and observed activity, then continue observation, cancel, or replace explicitly. Do not wait indefinitely on an outstanding request without reassessment.
- A finished job with a partial handoff, bare yield, or submission missing material acceptance/verification evidence ends that attempt only, not the task. Keep the task [~]; request missing evidence from an active worker or assign a fresh continuation if it has already ended. Never advance a gate from runtime completion status alone.
- Before deliberately replacing any flow subagent, and before stopping a paused attempt for the user or a blocker, Main MUST instruct the outgoing agent to write a **detailed, durable, attempt-scoped handoff** as a separate file under the assigned project's `artifacts/` directory (or the explicit assigned output root for non-project work) and receive a matching acknowledgment with the saved path before ending or cancelling that agent. A compact chat summary, a plan entry, or a delivery receipt is insufficient. The handoff preserves task/attempt/runtime-agent IDs and role, goal/criteria, current state and changed paths/ownership, decisions and rationale, verified commands/results, tried/rejected hypotheses, unresolved findings/blockers, remaining criteria, next safe actions, and references to all relevant earlier attempts/agents and their records/history. Keep prior attempt handoff files readable; do not overwrite them with the successor's outcome. Main receives only the compact acknowledgment and references, not the detailed handoff.
- Main MUST include that handoff reference and an explicit related-attempt list in the successor's assignment: task ID, attempt ID, runtime agent ID, role, artifact/report/checkpoint path, actual history URI (for example `history://<runtime-agent-id>` when exposed), and relevant history ranges/events when known. Include all relevant earlier attempts, not only the immediate predecessor. Explicitly authorize the successor to read those histories and records directly through supported read tools; do not mistake the task item's `tools` field for a history-access grant or fabricate IDs, URIs, or permissions.
- The successor MUST read the detailed handoff and relevant prior history before continuing substantive work, identify already verified results and rejected approaches, and report missing/unreadable references. Prior evidence is context, not fresh approval; check current source state before relying on it. If runtime/tool restrictions prevent history access, surface the limitation rather than claiming that access was granted. Main remains summary-only and does not relay full transcripts.
- After the handoff is saved, ensure the old job has ended or explicitly cancel it before launching the successor. Invalidate attempt/timer/advisor IDs and ignore stale events; keep the same task ID and a new attempt ID, with no overlapping implementation worker. If an unexpected forced stop or an already-ended agent makes the required handoff impossible, report the missing prerequisite and retain available records/history; do not fabricate the handoff or silently bypass the requirement. A replacement without the required handoff/history needs explicit user authorization for a recovery path.
- A paused attempt resumes on the same attempt ID when the user explicitly authorizes resumption; it needs no replacement handoff and no new job, and the prior handoff remains its state record.
- After two Silver implementation/correction attempts on the same task leave acceptance criteria unmet, Main reassesses the route before launching another attempt: it MAY propose Gold when the remaining obstacle is reasoning, root cause, design, or integration, and switches only within the user's routing authority or after asking. Missing inputs, access, or external dependencies must be resolved rather than disguised as a model problem. Count worker attempts, not tool retries or progress messages. There is no mandatory tier ladder and no automatic Gold promotion.
- The two-Silver-attempt route reassessment above and the 4–5-exchange checkpoint reuse existing attempt IDs and compact progress summaries; add no telemetry, persistent counters, or new supervision service. Reviewers and checkpoint executors remain in their dedicated roles; the progress checkpoint is not permission to reroute them into implementation workers.

### Main-brokered task-advisor consultations

- A worker may request diagnostic help before a timer fires when it has a bounded, evidence-backed unresolved technical question or material uncertainty that genuinely useful diagnostic input could inform, including competing plausible hypotheses with no safe discriminating next action. Repeated identical errors or failed hypotheses, no new evidence across distinct attempts, and an unchanged blocker without a discriminating next action are examples, not prerequisites. Elapsed time or a fixed attempt count alone is never sufficient; generic or open-ended task delegation does not qualify.
- A worker's `advisor_request` contains the matching `task_id`, `attempt_id`, a unique `consultation_id`, goal/criterion, current blocker, bounded relevant evidence/snippets, tried hypotheses and their results (or an explicit statement that none were safely tested yet), constraints, and one exact actionable question. Do not send full conversations, trajectories, histories, logs, or unrelated context. Workers never spawn advisors or change roles/models/config/depth themselves.
- The timer's `advisor_offer` is part of the existing progress request, not a separate message. `advisor_needed: false` is a cheap decline. A `true` reply, offer, elapsed time, or timer event alone never launches an advisor: Main requires a complete bounded `advisor_request` and validates that its exact question is actionable, the supplied evidence is relevant, and the request explains why diagnostic help is needed. A `true` without that payload is pending interest, not a consultation; do not re-offer or send a separate follow-up. The worker may add the complete request to its next normal progress reply or send one qualified request directly.
- Deduplicate by active task/attempt and blocker/criterion: do not launch or forward a duplicate while a request, pending interest, or consultation exists, and allow at most one active consultation per worker and two active subagents total. Omit further advisor offers while any request, pending interest, or consultation exists. Before asking again after a consultation, the worker must first try relevant advice and record the observed result, or provide genuinely new discriminating evidence.
- Main brokers a qualified request to a fresh `task-advisor` sibling, checks its effective definition/model and `blocking: false`, and confirms async execution is available before launch. Dispatch uses the `functions.task` tool API: with batch enabled, provide required `context` and one `tasks[]` item containing `agent`, `task`, and `solutionSpace`; with batch disabled, use one flat task item. The obsolete `task`/`hard-task` implementation agent roles are not valid `agent` values in this flow; use explicit `bronze-task`, `silver-task`, `gold-task`, `task-advisor`, `evidence-reviewer`, or `deep-reviewer`. The task item's `tools` field exposes parent eval-kernel tools; it is not an agent-tool whitelist. Omit a per-call `model` override for normal dispatch; the selected named definition supplies the current selector/effort. Check effective dispatch-time overrides without silently repairing them or creating new persistent model roles.
- Main forwards only the bounded request and routes a result back only when task, attempt, and consultation IDs all match. While it is pending, the worker continues only independent safe work; otherwise it waits for a completion/message event without redundant retries. Advice is diagnostic only, never implementation evidence, approval, or a gate verdict; the worker independently tries relevant advice and records the result.
- Before review, checkpoint execution, or replacement, Main resolves or explicitly cancels every outstanding consultation and invalidates its IDs. Worker completion, cancellation/replacement, and gate transition take precedence over late advisor output. Ignore stale results, even if their IDs otherwise look plausible.
- Before each advisor launch, Main checks effective project/user definitions and model overrides, then applies the dispatch-consent policy in the effective `task-advisor` definition. Model-specific approval restrictions belong in that definition, not this skill. When approval is required, tell the user the task and consultation IDs, exact resolved model/effort, and blocker/escalation reason; launch only after explicit approval scoped to that consultation. Silence, prior approval, urgency, failure, or approval of a different rollout is not consent. Record a bounded approval reference when applicable.
- Approval is one-use and bound to that task/consultation pair. After denial or while approval is pending, use only a verified configured default route that independently satisfies the same consent policy; otherwise wait and report the routing limitation. Never substitute a hardcoded fallback. If the dispatch schema cannot express an authorized override, report that limitation; do not invent syntax or change persistent defaults/configuration.
- The advisor remains read-only and distinct from OMP's built-in passive advisor. Do not change advisor configuration or recursion depth, or add cooldowns, enforced counters, or telemetry/logging. Record only a bounded consultation summary and attempted result in the worker's normal task artifact. Evidence and deep reviewers do not consume task-advisor consultations.

Before each advisor launch, Main verifies that the effective `task-advisor` definition is non-blocking and async execution is enabled. If either check fails, Main does not launch synchronously or silently alter configuration; it reports the condition and waits for an authorized resolution.

## Workflow

### 1. Resolve scope and route

Read `skill://manage-plans` for work needing durable planning. Main creates or updates ordered sprint tasks for large work; a bounded small fix needs no new sprint. Resolve acceptance criteria, the authorized repository/worktree and artifact root, then choose light or full with exact required gates. A sprint label alone never selects full.

### 2. Select and launch a worker

1. Apply the routing ask and scoped-authority rules above. Resolve current definitions and overrides; user-reported quota is ground truth, not something to re-measure to contradict the user. Bronze, Silver and Gold are selectable according to fit; uncertain Silver/Gold fit is a user tradeoff, not an implicit Gold promotion.
2. Brief one fresh async implementation worker with task/attempt IDs, criteria, authorized scope, route, required gates, selected role and selection basis, configured selector versus observed runtime selector (or `unknown`), relevant history refs, quota observation (or `unknown`), and the >5-minute notice rule. Include explicit repository/git-dir, worktree, `-C` root and target ref for project work, or an explicit non-project designation and output root.
3. State commit permission or its absence. A light worker may commit only its own verified scope when explicitly authorized with staging ownership; push needs separate authorization. If review is assigned before commit, obtain its matching PASS first. Mixed ownership or unrelated staged changes must not enter the commit: use only safely isolated, wholly owned content with scoped standard porcelain; otherwise report `commit_pending` without altering user state. Never blanket-stage, bypass hooks/signing, amend or rewrite history.
4. Require a worker summary only when an assigned gate or meaningful evidence preservation needs one. Give its exact repository-local artifact path then; ordinary light work may return a compact verified result without a template or manifest. Keep an existing plan task [~] until its assigned criteria and gates are satisfied.
5. For continuation/replacement, enforce the saved-handoff acknowledgment, old-job termination, all relevant related-attempt/history references and explicit required history reads above. Track completion/message events, not polling. Reclassify each new task independently; findings require correction, not automatic escalation.

### 3. Apply assigned evidence gates

Full-route tasks require independent evidence review; light-route tasks require it only when explicitly assigned. With no review assigned, Main checks the matching completed worker's result against acceptance and its specific verification evidence.

For an assigned review:

1. Check the effective `evidence-reviewer` definition and async availability. Supply task/attempt IDs, criteria, changed scope, worker evidence, explicit repository/ref, source and worker-history access, any plan, and exact report path. A planned full-route checkpoint also requires the reviewer-owned frozen manifest described in `evidence-reviewer.md`.
2. Accept only the matching completed reviewer's verdict and actual report reference. A progress message, stale PASS, artifact alone or runtime completion is not a verdict. Add only concise current status/outcome references to a plan.
3. Actionable findings or material missing proof mean FAIL. Assign a fresh correction attempt with the findings and relevant prior handoff/history, then a fresh review at the same level. Once assigned, an optional light review is binding; neither smoke nor a worker commit bypasses FAIL.
4. PASS satisfies that review only. Light work may finish once its other assigned criteria, verification and any assigned commit succeed. Full project work remains in progress until the checkpoint succeeds at its pre-agreed task/batch boundary.

### 3a. Execute a required full-route checkpoint

Only at the pre-agreed boundary, after every included task's separate evidence PASS:

1. Main accepts only matching reviewer PASS references tied to the exact base, approved snapshot, scope and assigned repository/ref. A missing, stale, mismatched or uncertain reference is not authorization. Resolve ownership or obtain fresh review; do not broaden scope.
2. Assign a fresh async, non-blocking explicit `bronze-task` a checkpoint-only task; never Silver or Gold. Give it the PASS references, reviewer-owned manifest and `snapshot_sha256`, exact repository/git-dir, worktree, `-C` root, target ref, expected base SHA, approved scope and exact record path under the assigned repository's `artifacts/`. Use `artifacts/sprint-<N>/checkpoints/` for sprint work or `artifacts/<task-id>/checkpoints/` for standalone work. The executor changes no source, approves no review and never pushes.
3. The executor verifies the explicit repository, target ref/base, real index, worktree and ownership before committing. Check additions, deletions, modes and exact approved content. A path is eligible only when wholly task-owned, its current worktree exactly matches reviewed content, and it contains no unrelated user hunks. A path list is not ownership proof. Mixed ownership, base/content drift or an uncertain snapshot that cannot be safely separated leaves `commit_pending`; request ownership resolution or fresh review. Never infer a repository from cwd/home/ancestors.
4. Use standard Git porcelain, honoring identity, signing and hooks. If the real index has no unrelated changes and its staged tree equals the approved snapshot, ordinary `git commit` is appropriate. With unrelated staged paths, commit only fully owned paths matching the reviewed worktree using ordinary scoped porcelain such as `git commit --only -- <owned_paths>`; explicitly stage genuinely new owned paths only when needed. Otherwise stop: do not guess, craft a synthetic index, blanket-stage, force-add ignored artifacts, stash/reset/checkout user state, bypass hooks/signing, amend, rewrite history or push.
5. Immediately verify the target ref and expected parent/base, commit SHA, committed paths/content against the manifest, and post-commit cached diff/status. Remaining staged changes must preserve only the user's intended staged changes, without reversions of committed task paths. The executor owns these observations and PASS references in its checkpoint record; a byte-for-byte index comparison does not replace semantic staging checks.
6. Hook/signing/identity rejection, failed commit, changed base/ref, snapshot mismatch, unexpected staging or uncertain results leave `commit_pending`. Resolve the cause without discarding user state. Retry only the same unchanged approved snapshot and expected base/ref; changed content needs fresh PASS. Main accepts success only from the matching completed executor and its record, then updates concise plan status.

A shared atomic batch must be declared and approved as one checkpoint boundary before implementation. Each included task still receives its own evidence review; one frozen approved batch snapshot is checkpointed before work outside that boundary. Never combine unreviewed work or postpone an independent task's required checkpoint for convenience.

Missing repository authorization never reclassifies project work as non-project and never permits repository initialization or a fallback home/ancestor commit. Full project work with an unavailable required checkpoint remains `commit_pending`. Explicit non-project work uses its assigned output root and assigned gates without inventing a Git checkpoint.

Any correction after checkpoint uses a fresh worker and fresh assigned review before a separate new Bronze checkpoint; never amend or rewrite the earlier commit.

### 4. Run differential review only when assigned

After all assigned task reviews and required checkpoints pass, launch a fresh async `deep-reviewer` only when meaningful cross-task review is assigned. Give it criteria, verified light results, existing worker/review/checkpoint records, history access and exact report path. It hunts differential risk rather than rerunning passed checks or demanding unassigned gates.

Accept only its matching completed verdict. Actionable findings reopen the affected task; fresh corrections satisfy that task's assigned review/commit/checkpoint requirements before another required deep review. Assigned deep-review FAIL blocks completion; absence of an assigned deep review does not.

### 5. Complete and retire

Main marks [x] only after acceptance and material verification are supported, every assigned review has passed, any assigned commit has succeeded, every required full-route checkpoint has succeeded, and any assigned deep review has no actionable findings. Verified light work may finish uncommitted when no commit was assigned; failed or unavailable assigned commits remain `commit_pending`.

Keep required records readable and concise outcome links in any existing plan. No superseded attempt may advance a gate. End or explicitly cancel jobs that must not continue; Main interruption is not job cancellation. No extra review, checkpoint, deep review or artifact is created just to retire a light task.

## Scheduling rules

1. **Planning:** Main resolves scope, route, acceptance and any needed plan.
2. **Implementation:** one active implementation worker; an optional qualified advisor must fit the two-active limit.
3. **Assigned evidence review:** worker complete; one matching reviewer, only when required.
4. **Correction:** fresh worker attempt; fresh assigned review follows when applicable.
5. **Full-route checkpoint:** matching PASS and frozen snapshot; one fresh Bronze executor, no next independent task beyond the agreed boundary.
6. **Commit pending:** an assigned worker commit or required checkpoint failed/unavailable; no completion, and no crossing an unmet full-route boundary.
7. **Assigned deep review:** all prerequisite assigned gates passed; one differential reviewer.
8. **Complete:** criteria, verification and only the assigned gates satisfied; required jobs completed or explicitly cancelled.

Never exceed two active subagents total. Use completion/message events and `functions.wait` only when otherwise blocked; no polling or worker eval wait/barriers. An observation timer is a separate finite shell job, never a worker deadline. Keep pending gates in progress.

Routine dispatch, model, timer, progress and retry metadata stays in chat/trace, not sprint plans. Save a genuinely needed handoff or temporary supervision state separately under the assigned repository's `artifacts/`. Plans retain scope, acceptance, current status, milestones, durable decisions/blockers and concise verified outcome references only.

## Orchestrator output

Report the current task/attempt and selected route/role, configured versus observed runtime selector when relevant, quota observation or `unknown`, meaningful outcome/blocker, matching assigned gate results and actual record refs, and completion status. Never fabricate quota mechanics, history access, verification or provider-applied effort. Keep detailed implementation/review/Git evidence in its owner's record; do not return full transcripts or duplicate them in plans.
