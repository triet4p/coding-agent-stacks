# Foundry dataset contracts

Apply when producing or consuming Foundry datasets.

- **Cross-project dataset inputs come from the producer's `shared` layer.** Do not reference another project's internal `raw`, `clean`, `processed`, or `object` datasets directly. Within a Datasource project, `raw` represents source data ready for transformation; `clean` standardizes it; optional `processed` owns joins and complex transformations. A Datasource `shared` dataset projects an explicit schema from exactly one `clean` or `processed` input. No joins, unions, or new business calculations in `shared`.
- **Ontology owns use-case enrichment.** Join shared inputs and calculate use-case logic in Ontology `processed`; keep the `object` dataset as backing for an Object Type. Keep an Ontology `shared` output when it serves a real publishing boundary. Do not add an identical copy solely to fill a layer.
- **Every `shared` output declares its grain, schema, primary key, and null policy.** Grain says what one row represents. The published primary key may be a single column or a composite key. Enforce uniqueness and non-nullness of the published key after normalizing or encoding it, across the complete published dataset rather than just the current batch. If publishing a tuple as the key, enforce non-nullness of each key component. If publishing an encoded key, document component null semantics and use an unambiguous encoding that distinguishes null from literal values.
- **Do not hide key collisions.** If distinct entities at the stated grain collapse to the same key, find a stable discriminator that represents identity at that grain or report missing source identity. If the rows are genuinely the same entity, consolidate only under a documented domain rule. Do not drop duplicates, fill nulls with a sentinel, or add volatile columns merely to pass a key check.
- **Prefer natural or source-assigned keys.** Use a hash only when there is no reliable natural or source-assigned key at the declared grain. Define stable, canonical inputs and verify the resulting key stays unique and stable across rebuilds. Hashing identical inputs cannot distinguish different entities; report that case instead of claiming a valid key.
- **Joins declare expected cardinality and output grain.** Validate the unique side before joining and check the resulting grain. If the contract preserves fact rows, do not silently discard rows with missing FK values or values that have no match. Check key expectations from `clean` onward wherever the layer declares a key or depends on its uniqueness.
